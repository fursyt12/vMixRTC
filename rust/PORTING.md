# Rust-порт vMixUTC — план и текущее состояние

Цель: контроллер vMix, который запускается не только на Windows, но и на Linux/ARM
(одноплатники) и на планшетах. vMix — Windows-only приложение, поэтому вне Windows
порт работает как удалённый контроллер через Web API vMix (`http://host:8088/api`).

Работа ведётся локально: **в upstream/форк ничего не пушится**, пока не решено иначе.

## Что берём из оригинала, а что переписываем

| слой оригинала | объём | в порте |
|---|---|---|
| `vMixAPI/` (подключение, состояние, функции) | 26 файлов, 2 718 строк | **переносится**: крейт `vmix-api` |
| `.vmc` (`.NET XmlSerializer` контроллера) | формат XML | **переносится**: крейт `vmix-config` |
| `IvMixDataProvider` + json/xml/excel/sheets/filesystem | ≈ 4 100 строк | **переносится** (данные): крейт `vmix-providers`; WPF-часть (`ShowProperties`, `CustomUI`) уходит в UI |
| `Classes/Scripting` + `Functions.xml` / `NewFunctions.xml` | 459 + 811 функций | **переносится**: крейт `vmix-functions` (каталог, команды, рендер запросов) |
| действия кнопок в `.vmc` (`<Commands>`) | формат XML | **переносится**: `vmix-config::WidgetCommand` |
| приложение, виджеты, редактор, скрипты | ≈ 25 000 строк C# | **переписывается** |
| 40 файлов XAML (шаблоны, стили, темы) | ≈ 8 200 строк | **переписывается** — WPF-шаблоны в другой UI-стек не переносятся |
| `NDILibDotNet2` / `vMixStreamDeckLibrary` / MIDI / OMT / LTC | ≈ 9 000 строк + native | **через FFI или заново**, см. матрицу платформ |

Ключевое ограничение: визуал виджета в оригинале выбирается по имени C#-типа
(`TypeTemplateSelector` ищет `DataTemplate` с ключом `{ИмяТипа}`), поэтому `.vmc`
переносится как данные, но каждое визуальное представление пишется заново.

## Команды кнопок и функции vMix

Оригинал держит действия кнопки в `<Commands>` внутри `.vmc`, причём сигнатуру функции
несёт сама команда (`<Action><FormatString>…`). Благодаря этому порт исполняет команды
любого существующего контроллера и пишет свои так, что их понимает оригинал.

| что | где |
|---|---|
| каталог функций: `Functions.xml` (классические кнопки, `{0}…{8}`) и `NewFunctions.xml` (новые, `$InputKey`/`$Value`/`$Mix`) | `vmix-functions::Catalogue` |
| поиск каталога: `VMIX_FUNCTIONS_DIR` → каталог exe → `vMixController/` → `../vMixController` | `Catalogue::discover()` |
| подстановка плейсхолдеров (`{0}` — ключ входа, если задан, иначе номер — как в `vMixControlButton.cs`) | `FunctionRef::render()` |
| команды в `.vmc` (`Input`, `InputKey`, `Parameter`, `StringParameter`, флаги `IsExecutable`/`UseInActiveState`) | `vmix-config::WidgetCommand` |
| нажатие: рендер → GET к vMix → журнал «запрос → ответ» | `vmixrtc::press_commands`, IPC `vmix_press` |
| редактор команд в свойствах кнопки: список, ↑/↓, ▶, ✕, добавление по каталогу | `app.js::appendCommandsEditor` |
| режим пульта: `WindowSettings.Locked` (сохраняется в `.vmc`) — виджеты исполняются, а не редактируются | IPC `vmc_set_locked`, кнопка «🔓 Редактор / 🔒 Пульт» |

Кнопки-переключатели (`Style` = Toggle) меняют `Active`/`IsPushed` в файле.

### Состояние по данным vMix

Подсветка кнопок считается по состоянию vMix — порт
`vMixControlButtonHelper.CalculateStateDependency`:

| что | где |
|---|---|
| опрос: один запрос отдаёт и состояние для панели, и «нажатость» виджетов | `vmixrtc::vmix_poll` (IPC) |
| вычисление: подстановка аргументов в `ActiveStateXPath`, чтение значения из XML, сравнение с `ActiveStateValue` | `vmix-functions::state::evaluate` |
| операторы сравнения: `!` — отрицание, `~` — содержит, `` ` `` — не содержит, `*` — любое, `-` — пусто | `values_match` (порт `ValuesMatch`) |
| минимальный XPath (`//a/b[@attr='v']/@attr`) — покрывает 29 форм из каталогов | `xpath_value` |

### Редакторы свойств и планировщик

* **Свойства по типам**: панель показывает поля, зависящие от типа виджета (стиль и автозапуск
  кнопки, цель и вход громкости, ориентация TBar, формат часов, переменная для просмотрщика,
  режимы списков). Реализовано описанием полей в интерфейсе вместо 15 XAML-редакторов
  оригинала; выбор входа берётся из живого состояния vMix, выбор переменной — из документа.
* **Планировщик часов** (`SchedulerControl` в оригинале): события «время + дни недели + ссылка»,
  проверка раз в секунду, запуск через тот же диспетчер ссылок; срабатывание один раз в сутки,
  сброс при смене даты, защита от длинных цепочек `ExecLink` (аналог `ScriptExecutionLoopGuard`).
  Логика проверки — чистая функция с тестом на дни недели, время и повторный запуск.

## Локализация

Строки живут в словарях `crates/vmixrtc/ui/locales/{ru,en}.json` — это **один источник** и для
Rust, и для интерфейса (JS читает те же файлы из собранного фронтенда). Соответствие оригиналу:
`LocalizationManager` + ключи `loc:Loc`; язык хранится в настройках, каталог настроек зависит от
платформы (Linux — `XDG_CONFIG_HOME`, macOS — `Application Support`, Windows — `APPDATA`,
мобильные — внутренний каталог приложения).

| что | где |
|---|---|
| словари (190 ключей, паритет ru/en) | `crates/vmixrtc/ui/locales/*.json` |
| загрузка, подстановка `{0}`, определение языка (`VMIXUTC_LANG` → `LC_ALL`/`LANG`) | `crates/vmixrtc/src/i18n.rs` |
| команды `language`/`set_language`, выбор языка в панели | `vmixrtc` + UI |
| ключ локализации вида виджета (`kind.button`, …) | `WidgetKind::localization_key` |

Проверки в тестах: паритет ключей, отсутствие пустых значений, одинаковое число подстановок,
**каждый ключ, который использует интерфейс (`t("…")` и `data-i18n`), обязан быть в словарях**,
и у каждого вида виджета/провайдера есть перевод.

## Сборка под платформы

Проверка переносимости — `./check-targets.sh` (`cargo check` по крейтам для Linux x86_64/ARM64,
macOS ARM64, iOS ARM64 и Android ARM64). Ядро (`vmix-xml`, `vmix-config`, `vmix-functions`,
`vmix-script`), NDI, MIDI и Stream Deck собираются под **все** цели; `vmix-api`/`vmix-providers`/
`vmixrtc-cli`/`vmixrtc` требуют C-тулчейна целевой платформы (`ring` для TLS): кросс-gcc для ARM, Xcode
для Apple, NDK для Android — это стандартное требование кросс-сборки, а не ошибка кода.

MIDI и Stream Deck объявлены как платформенные фичи: на мобильных крейты собираются без нативных
бэкендов и возвращают понятное сообщение вместо ошибки. Настройки Tauri для Android/iOS
(`bundle.android`, `bundle.iOS`, набор иконок, общие capabilities) уже прописаны.

Подробные команды и требования — в **[BUILD.md](BUILD.md)**.

## Провайдеры данных

Виджет внешних данных (`vMixControlExternalData`) держит провайдера так: путь
(`DataProviderPath`), список свойств (`DataProviderProperties`) и **встроенную .NET-сборку**
(`DataProviderContent`, base64). Виджеты-потребители (`List`) ссылаются на источник по имени
через `DataSource` и несут карту путей `<Paths>`.

**Осознанное отличие:** Rust не исполняет .NET-сборки, поэтому порт игнорирует
`DataProviderContent` (узел сохраняется в файле как есть) и выбирает **встроенный** провайдер
по `DataProviderPath`. Свойства читаются ровно те, что положил оригинал, — `.vmc` совместим
в обе стороны.

| что | где |
|---|---|
| определение провайдера по `DataProviderPath` (`XmlDataProvider.dll` → XML и т. д.) | `vmix-providers::ProviderKind::from_path` |
| XML-провайдер: свойства `[url, xpath, namespaces, groupBy]`, источник — `http(s)`, `file://` или путь | `XmlDataProvider` (порт `vMixGenericXmlDataProvider`) |
| объединение XPath через `|` в порядке документа + склейка строк по `GroupBy` через `\|` | `rows_from_xml` |
| выборка всех совпадений XPath (`@number`, `@title`, вложенные элементы) | `vmix-functions::xpath_select` |
| применение строки к тайтлам: пары `Paths`, позиционные значения, `RestartData`, хук `@[cmd]` | `vmixrtc::apply_external_row` (порт `UpdateText`) |
| связь «виджет-источник → потребитель» по имени `DataSource` | `refresh_externals` |
| отрисовка строк в виджете и клик по строке | `app.js` (`externalApply`) |
| настройки: источник, XPath, период, виджет-источник, карта путей | свойства виджета |

Проверено на реальном `InputSelector.vmc`: провайдер XML читает состояние vMix по адресу из
файла с XPath `./vmix/inputs/input/@number|./vmix/inputs/input/@title` и `GroupBy=2` — строки
получаются `1|Text Middle Centre.gtzip … 5|Blue` (ровно то, что оригинал записал в поле
`Text`). Выбор строки уходит в vMix как
`Function=SetText&Input=<ключ>&SelectedIndex=1&Value=5%7CHeadline` (тест
`external_widget_reads_provider_and_applies_row`).

### Реализованные провайдеры

| провайдер | свойства (как в `.vmc`) | источник | примечание |
|---|---|---|---|
| XML | `[url, xpath, namespaces, groupBy]` | `http(s)`, `file://`, путь | объединение XPath через `\|`, склейка строк по `GroupBy` |
| JSON | `[url, jsonPath, groupBy, headers]` | `http(s)`, `file://`, путь | подмножество JSONPath: `$`, `.имя`, `['имя']`, `[n]`, `[*]`, `..имя`; заголовки HTTP строками «Имя: значение» |
| Excel | `[filePath, startRow, endRow, startCol, endCol, sheetIndex, isTable]` | файл `.xlsx/.xls/.ods` (crate `calamine`) | лист по имени или номеру, срез колонок буквами (`A`…`AB`) или числами, `IsTable` — строка через `\|` |
| **Google Sheets** | `[apiKey, startRow, endRow, startCol, endCol, sheetIndex, isTable, sheetKey, period]` | Google Sheets API v4 | ссылку на таблицу можно вставить целиком — ключ извлекается; `includeGridData=true`, как `Popcron.Sheets` |
| **NDI** | `[sourceName, null, multiViewLayout, aspectRatio, isAudioEnabled, isLowBandwidth]` | NDI runtime (FFI) + NDI-входы состояния vMix | список источников из состояния vMix и **видео** через `vmix-ndi` (MJPEG в webview); без runtime — тестовый сигнал |
| Файлы | путь к каталогу | локально | список файлов (ядро, UI ещё нет) |

«HTTP API» — это не отдельный провайдер, а режим источника: и XML-, и JSON-провайдер умеют
тянуть данные по `http(s)://` (у JSON — с произвольными заголовками), поэтому любой HTTP API,
отдающий XML или JSON, подключается парой «URL + путь». Проверено тестом, который поднимает
мок-сервер и убеждается, что заголовок `X-Api-Key` реально ушёл по проводу.

### NDI: приём видео

Оригинал показывает NDI-монитор WPF-контролом (`CustomUI` провайдера, `ReceiveView`). В порте
интерфейс — webview, поэтому кадры отдаются **MJPEG-потоком** и подставляются в `<img>`: без
IPC на каждый кадр и без декодера в JS. Крейт `vmix-ndi`:

| что | где |
|---|---|
| конвертация кадров NDI (`UYVY`, `BGRA/BGRX`, `RGBA`, `RGB`) в RGB | `Frame::to_rgb` |
| JPEG-энкодер и MJPEG-сервер (`multipart/x-mixed-replace`) | `MjpegServer` |
| синтетический источник (тесты и демонстрация без runtime) | `TestBackend` |
| NDI runtime через FFI: `NDIlib_initialize/find_*/recv_*` (libloading) | `RuntimeBackend` |

В приложении поток поднимается автоматически для виджета с NDI-провайдером
(`ensure_ndi_stream`): если NDI runtime найден — приёмник подключается к источнику из свойств
провайдера, если нет — показывается тестовый сигнал с пометкой причины. Кадры идут в `<img>`
виджета, кнопка «NDI: остановить поток» — команда `ndi_stop`.

**Честно про FFI:** биндинги написаны по публичным заголовкам NDI 5 и загружаются динамически
(`libloading`), поэтому крейт собирается без установленного NDI. Проверить их в бою можно только
на машине с NDI runtime — в этом окружении его нет, поэтому FFI покрыт компиляцией и проверкой
аккуратного отказа, а весь остальной конвейер (конвертация → JPEG → MJPEG → `<img>`) проверен
тестами и скриншотом с тестовым сигналом.

Ещё не сделано: звук NDI, mDNS-обнаружение без runtime, режим триггеров `@[cmd]` (оригинальный
`Values` NDI-провайдера работает именно так) и выбор источника прямо из списка найденных.

### Виджеты: часы, громкость, TBar, просмотр переменных

Добавлены к уже перенесённым (область, кнопка, текст, счёт, таймер, список, плейлист, внешние
данные). Свойства читаются из `.vmc` через `WidgetData.extras` (явный список тегов, чтобы в него
не попали блобы вроде `DataProviderContent`), а поведение повторяет оригинал:

| виджет | поведение | что уходит в vMix |
|---|---|---|
| `vMixControlClock` | часы идут локально, раз в секунду: время, секунды, дата, UTC по свойствам | ничего |
| `vMixControlVolume` | вертикальный фейдер + кнопка звука, значение берётся из состояния | `SetVolume`/`SetMasterVolume`/`SetBus?Volume` с кривой оригинала `Value = 100·(v/100)^¼`; состояние → фейдер обратной кривой; mute — `AudioOn`/`AudioOff` (`Input` или `Value=<шина>`) |
| `vMixControlTBar` | перетаскиваемая ручка 0…255 | `Function=SetFader&Value=<0…255>` — как оригинал, готовой строкой |
| `vMixControlVariableViewer` | показывает значение глобальной переменной, при `ShowVariableName` — и её имя | ничего (значение из документа) |

Проверено на сгенерированном контроллере: `vmixctl demo docs/demo-widgets.vmc` создаёт по виджету
каждого типа палитры (11 штук) — удобно и для проверки, и как пример.

### Stream Deck

**Отличие от оригинала (осознанное).** В C# контроллер **не общается с устройством напрямую**:
он подключается к плагину Elgato (`vMixUTCStreamDeck.exe`) через WebSocket, а плагин присылает
`KeyDown`/`KeyUp` с «контекстом» кнопки. Порт говорит с устройством **сам, по HID** — так не
нужны ни Stream Deck Software, ни .NET-плагин, что и есть цель форка. Поле `Context` из `.vmc`
сохраняется для совместимости, но роль контекста играет индекс кнопки.

| что | где |
|---|---|
| модели устройств по `product_id` (15/6/32/8 кнопок, длина отчёта, ручки) | `vmix-streamdeck` |
| разбор входных отчётов в события с фронтами «нажал/отпустил» | `DeckState::apply` |
| яркость подсветки | `DeckState::brightness_report` |
| источник событий: реальный HID (`hidapi`) или тестовый | `runtime::RuntimeSource`, `TestSource` |
| кнопки виджета (`Keys`: индекс → ссылка) и обучение | `vmix-config`, `vmixrtc` + UI |

Ссылку запускает именно **отпускание** кнопки (`KeyUp`) — как в оригинале. Цепочка
«кнопка → ссылка → скрипт → vMix» покрыта тестами (разбор отчётов, фронты, поиск ссылки,
диспетчер). С настоящим устройством не проверено: в этом окружении Stream Deck нет, поэтому
виджет показывает «тестовый Stream Deck (устройство недоступно: …)» и подставляет тестовые
события.

Ещё не сделано: вывод картинок на кнопки (JPEG с поворотом), поворот ручек Stream Deck +,
кнопка «назад» у XL, экраны у Neo.

### Ссылки, горячие клавиши и MIDI

Оригинал связывает всё через **ссылки**: у каждого виджета есть записи `Hotkey` (`Name`, `Link`,
`Key`, `Ctrl/Alt/Shift`, `OnPress`, `Active`), а `MainViewModel.ProcessHotkey` по имени ссылки
запускает действия **всех** виджетов, которые её слушают. MIDI, Stream Deck, скрипты и таймеры
шлют одно и то же сообщение `HotkeyLinkMessage { Link, Parameter }` — то есть источники ничего
не знают о виджетах.

Порт:

| что | где |
|---|---|
| разбор `Hotkey` из `.vmc` и поиск целей по ссылке (`hotkey_targets`) | `vmix-config` |
| правка ссылки/активности из интерфейса (`vmc_set_hotkey`) | `vmixrtc` |
| диспетчер ссылок: «Execute» у кнопок прогоняет скрипт, значение приходит в выражение как `_param` | `vmixrtc::dispatch_link` |
| MIDI: сообщения, отображения, `midir` и тестовый источник | крейт `vmix-midi` |
| MIDI-виджет: лицо, выбор входа, запуск/остановка, отображения, обучение по последнему сообщению | `vmixrtc` + UI |

Виртуальные кнопки из палитры сразу получают штатные ссылки (`Execute`, `Reset`,
`Clear Variables`, `Press`, `Release`) — как в `.vmc`, созданных оригиналом.

**Честно про MIDI:** цепочка «сообщение → отображение → ссылка → скрипт → vMix» проверена тестами
(в том числе на двух заглушках vMix), а `midir` собирается и работает с ALSA. Проверить с
настоящим MIDI-пультом в этом окружении нельзя: в песочнице нет ALSA-секвенсора (`/dev/snd/seq`),
поэтому виджет честно показывает «тестовый MIDI (устройство недоступно: …)» и подставляет
тестовые сообщения.

### MultiState, Slider, Container

* **`vMixControlMultiState`** — не «кнопка с состояниями», как можно подумать по имени, а
  **ретранслятор**: он подписан на `State.OnFunctionSend` и, если включён, отправляет каждую
  функцию основного контроллера во **второй vMix** (`IP`/`Port`/`Login`/`Password`). В порте
  это `VmixClient`-ы из `Vmc::relay_targets()`: каждая отправка (скрипт кнопки, `vmix_call`,
  применение строк) повторяется ретрансляторам, а в журнал попадают строки `↔ host:port: ок`.
  Сбой ретрансляции не рвёт основной поток — как и в оригинале.
* **`vMixControlSlider`** — устаревший алиас `vMixControlVolume` (в C#: `class ... : vMixControlVolume`),
  поэтому рендерится и работает как громкость.
* **`vMixControlContainer`** — контейнер, в который импортируется другой `.vmc`
  (`AfterPropertiesChanged`: координаты сдвигаются к `(0,0)`, ширина подгоняется под содержимое,
  `FilePath` после импорта очищается). В порте: `Vmc::import_into_container` (CLI
  `vmixctl container <файл> <индекс> <источник>` и кнопка «Импортировать» в свойствах),
  вложенные виджеты читаются из `<Controls>` и рисуются внутри контейнера; в режиме пульта
  нажатие вложенной кнопки уходит с параметром `container`, а рантайм скриптов ведётся по
  составному ключу, чтобы переменные вложенных кнопок не пересекались с верхними.

### Просмотр строк и `IsMappedToGUID`

* **`RowsViewer`** (порт `vMixControllerSkin/RowsViewer.xaml`): окно показывает строки источника
  таблицей — каждая строка разбивается по `|` на ячейки (как конвертер `StringToGridTable`).
  Открывается кнопкой «Показать строки источника» в свойствах или двойным щелчком по виджету;
  в шапке — имя провайдера, число строк и ошибка источника, если она есть.
* **`IsMappedToGUID`**: в оригинале это свойство **только хранится и правится в редакторе** —
  во всём C#-коде оно объявлено в `vMixControlTextField.cs` и нигде не читается (проверено
  поиском по репозиторию). Порт трактует его по смыслу: `true` — `Paths` ссылается на вход по
  ключу (GUID), `false` — по номеру (с поиском по ключу как запасным вариантом).

Ещё не сделано совсем: отдельное окно свойств провайдера (`PropertiesWindow`, `OnWidgetUI`) —
сейчас настройки правятся в свойствах виджета, поля зависят от типа провайдера.

### Порядок отрисовки

Виджеты рисуются по `ZIndex`, при равенстве — в порядке файла, как в оригинале. Видео NDI
занимает ровно область виджета (`overflow: hidden` у контента, `object-fit: contain`), поэтому
сквозь монитор ничего не просвечивает: если у монитора `ZIndex` выше, кнопки под ним не видны
(проверено скриншотом). Элемент `<img>` переиспользуется между перерисовками, иначе браузер
переподключался бы к MJPEG на каждое обновление состояния.

## Скриптовый слой

Скрипт кнопки — список команд с управляющими функциями UTC. Порт исполняет их
(`vmix-script`), соответствие — `vMixControlButton.ExecutionThread` и
`CalculateExpression`.

| что | где |
|---|---|
| выражения: литералы, `_('путь')`, переменные `_varN`, `+ − * / %`, сравнения, `&&`/`||`/`!`, `len()` | `expression.rs` |
| интерпретатор: стек условий, `Condition`/`Else`/`ConditionEnd`, `IsPressed`, `HasVariable` | `interpreter.rs` |
| задержки и переходы: `Timer`, `Delay`, `GoTo` (с защитой от зацикливания) | там же |
| переменные: локальные (живут между нажатиями), глобальные → в `GlobalVariables` файла | `WidgetRuntime` в `vmixrtc` |
| `ValueChanged`, `API`/`APIPOST`, `NextPage`/`PrevPage`/`SetPage` | там же |
| прогон скрипта без интерфейса | `vmixctl press <файл.vmc> <индекс>` |

Точности, найденные по коду оригинала и проверенные на реальном `Scoreboard.vmc`:

* «объект-параметр» всегда берётся из `StringParameter` (вычисленный) — как
  `CalculateObjectParameter`, а не из `Parameter`/`FloatParameter`;
* ключ входа берётся из самой команды (`cmd.InputKey`), а не из контекста запуска;
* `Overlays[N].ActiveInput` — свойство-объект, поэтому в выражениях даёт **номер** входа,
  а не ключ; иначе реальное условие
  `_('Overlays[0].ActiveInput') != _('Inputs[{0}].Number')` из `Scoreboard.vmc` было бы
  всегда истинным;
* управляющие функции исполняются даже внутри ложного блока (как в оригинале) — иначе
  вложенные условия и `Else` работают неправильно.

Проверка на живом скрипте (`vmixctl press` + мок vMix): при пустом оверлее ветка «тогда»
шлёт `OverlayInput1Out`, ждёт `Timer` 750 мс и шлёт `OverlayInput1In`; когда оверлей уже
показывает этот вход — условие ложно и уходит только `OverlayInput1In`.

### Редактор скрипта

Скрипт собирается в модальном редакторе (свойства кнопки → «Открыть редактор скрипта»):

* список команд с номерами, галочкой «исполнять» (`IsExecutable`) и превью параметров
  (`Функция(<вход>, значение, параметр)`, как `ToString()` в оригинале);
* раскрытие команды: функция выбирается из каталога, поля строятся по её сигнатуре —
  вход (список входов из живого состояния vMix), числовой параметр, значение, float;
* у `Condition` — четыре дополнительных параметра (`Значение {1}`, `Выражение 1`,
  `Оператор` с подсказкой `= != > < >= <= ~ \``, `Выражение 2`) и напоминание, что
  выражения читают состояние через `_('…')`;
* перестановка ↑/↓, дублирование, удаление, «Очистить»;
* импорт/экспорт скрипта текстом (по строке на команду): экспорт — `Command::to_text()`,
  импорт — `Command::parse_with_signature()` (разбор по сигнатуре функции, как
  `vMixControlButtonCommand.FromString`), метаданные функции подтягиваются из каталога;
* dev-удобство: `vmixui <файл.vmc> <индекс> script` открывает редактор сразу.

Ещё не сделано в редакторе: перетаскивание строк мышью, подсветка синтаксиса в текстовом
виде, кнопка «T» (подстановка индекса тайтла), валидация выражений на лету.

Реализовано 12 нативных функций (`Condition`, `Else`, `ConditionEnd`, `IsPressed`,
`HasVariable`, `SetVariable`, `SetGlobalVariable`, `ValueChanged`, `Timer`, `Delay`,
`GoTo`, `API`/`APIPOST` и команды страниц). Остальные из 27 (`Win`, `ExecLink`, `LIVE*`,
`Sync*`, `SetButtonColor`, `If`/`EndIf`) помечаются в журнале и в vMix не уходят.

**Отличие от оригинала (осознанное).** В нынешнем оригинале состояние считается только по
`ActiveStateXPath`, а старый `ActiveStatePath` (`Overlays[{3}].ActiveInput`,
`Inputs[{0}].State`, …) не вычисляется вовсе — поэтому в `.vmc`, где команды хранят только
его (например, во всех `Examples/*.vmc`), кнопки не подсвечиваются и в оригинале. Порт умеет
оба: если XPath нет, `legacy_xpath()` переводит старый путь в XPath (23 формы из каталогов),
так что подсветка работает и на старых контроллерах. Проверки —
`state.rs::legacy_paths_from_the_catalogues_are_translated` и
`vmixrtc::widget_states_come_from_vmix_state` (реальный `Scoreboard.vmc` + состояние с оверлеем).

## UI-стек: Tauri

Выбран Tauri v2: интерфейс — обычный HTML/CSS/JS (лучший тач и мультитач, в перспективе
Android/iOS), ядро остаётся в Rust, связь — через IPC-команды.

```
crates/vmixrtc/
  src/main.rs        команды: vmix_state, vmix_call, vmc_summary
  build.rs           tauri_build::build()
  tauri.conf.json    окно, withGlobalTauri: true, frontendDist: ../ui
  capabilities/      разрешения окна (core:default)
  ui/                статический фронтенд: index.html + app.js + styles.css
```

Сборщик не нужен: `app.withGlobalTauri = true`, поэтому фронтенд обращается к
`window.__TAURI__.core.invoke` без npm-пакетов и бандлера.

Зависимости платформы (Linux): `webkit2gtk-4.1`, `javascriptcoregtk-4.1`, `libsoup-3.0`,
`gtk+-3.0` — в этом окружении уже установлены (webkit2gtk 2.52.6).

## Как собирать

`cargo` в этом окружении не может писать в `~/.cargo`, поэтому используем обёртку,
которая держит реестр внутри проекта:

```bash
cd rust
./cargo.sh build            # сборка
./cargo.sh test             # тесты, включая golden-тесты на Examples/*.vmc
./cargo.sh run -p vmixrtc-cli -- vmc ../vMixController/Examples/Scoreboard.vmc
./cargo.sh run -p vmixrtc-cli -- status --host 127.0.0.1 --port 8088
./cargo.sh run -p vmixrtc    # тач-панель (окно Tauri)
./cargo.sh run -p vmixrtc -- ../vMixController/Examples/Scoreboard.vmc   # сразу открыть контроллер
```

Инсталляторы/бандлы требуют Tauri CLI (в этом окружении его нет):

```bash
cargo install tauri-cli --version "^2"   # либо npm i -D @tauri-apps/cli@^2
cd rust/crates/vmixrtc && ../../.cargo/bin/cargo-tauri build
```

Живой тест против реального vMix:

```bash
VMIX_HOST=127.0.0.1 ./cargo.sh test -p vmix-api -- --ignored
```

## Риски и открытые вопросы

* **Скрипты**: `SafeExpression` — часть пропатченного форка NCalc. Нужно либо
  повторить синтаксис выражений в Rust, либо встроить совместимый вычислитель.
  Это обязательный пункт для паритета: от него зависят кнопки и состояния.
* **NDI/OMT**: лицензии SDK и наличие ARM-сборок; проверить до фазы 7.
* **Тач на планшетах**: в веб-стеке (Tauri) тач-жесты и мультитач богаче, чем в
  нативных GUI-крейтах; если планшеты — приоритет, стек стоит выбирать до фазы 3.
* **Формат `.vmc`**: порт обязан писать файлы, которые читает оригинал (обратная
  совместимость), иначе теряется совместимость с существующими настройками.
* **Проверка на реальном vMix**: golden-тесты покрывают формат, но не протокол;
  нужен стенд с vMix для тестов «живьём».
